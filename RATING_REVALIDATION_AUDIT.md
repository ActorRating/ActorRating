# Rating submission – revalidation audit

Audit of all revalidation triggers when a rating is submitted (create or update).  
Searched for: `revalidatePath`, `revalidateTag`, `unstable_cache`, `dynamic = "force-dynamic"`, and `revalidate`.

---

## 1. Every file where revalidation happens

### 1.1 `revalidatePath` / `revalidateTag`

**No on-demand revalidation on rating submit.**

| File | Usage |
|------|--------|
| `src/app/api/ratings/route.ts` | **None.** Comment only: "No per-rating revalidatePath — reduces ISR writes; dashboard uses revalidate: 600 and client refetch after submit". |
| `src/app/api/ratings/[id]/route.ts` | **None.** Comment only: "No per-rating revalidatePath — reduces ISR writes; client updates state; /r/[slug] uses revalidate: 60". |

There are **no** `revalidatePath` or `revalidateTag` calls anywhere in the app. Rating create/update does **not** trigger any path or tag revalidation.

## 2. Which pages get regenerated when a rating is created

**None.**

- No `revalidatePath` or `revalidateTag` is called in the rating APIs.
- No server actions or other code paths call revalidation on rating create/update.
- Regeneration only happens when:
  - A user (or bot) requests a page that is past its `revalidate` window, or
  - A route uses `unstable_cache` and the cache TTL has expired on next request.

So **a single rating submission does not trigger regeneration of any page.**

---

## 3. How many ISR writes a single rating submission likely triggers

**Zero** from the rating flow itself.

- **On submit:** Only the rating API runs (POST or PUT). It does not call `revalidatePath` or `revalidateTag`. No ISR write is triggered by the submit.
- **Later:** ISR writes occur only when:
  - Someone visits `/r/[slug]` after 60s → that share page may revalidate.
  - Someone visits `/actors/[id]` or `/movies/[slug]` after 1h → those pages may revalidate.
  - Someone visits a rate page after 24h → that page may revalidate.

So **per rating submission: 0 ISR writes**. Any ISR writes are from normal time-based revalidation on subsequent traffic, not from the submit.

---

## 4. Whether any duplicate revalidation exists

**N/A.** There is no on-demand revalidation on rating submit, so there is no duplicate revalidation in this flow.

(If you later add `revalidatePath` in the rating APIs, avoid calling it multiple times for the same path or in both a try and a catch block.)

---

## 5. Whether actor, movie, and performance pages are revalidated separately

**They are not revalidated on rating submit.**

- **Actor pages** (`/actors/[id]`): Use `revalidate = 3600`. No `revalidatePath` on rating. They revalidate only when requested after the 1h window.
- **Movie pages** (`/movies/[slug]`): Use `revalidate = 3600`. No `revalidatePath` on rating. Same time-based behaviour.
- **Rate page** (`/rate/[movieSlug]/[actorSlug]`): Uses `revalidate = 86400` and `unstable_cache`. No invalidation on rating.
- **Share page** (`/r/[slug]`): Uses `revalidate = 60` and `unstable_cache`. No invalidation on rating.
- **Performance page** (`/performances/[id]`): Uses `dynamic = "force-dynamic"` (client page). No cache; not revalidated by rating.

So **actor, movie, and performance/rate/share pages are not revalidated separately (or at all) by a rating submission.** Freshness for actor/movie is currently achieved by:
- Client-side refetch with cache-busting (e.g. `?_t=...`) when returning to actor/movie pages (e.g. from success page).
- Time-based ISR when the revalidate interval has passed.
